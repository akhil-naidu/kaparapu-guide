Chapter 06 of 12

A clean tracker and neutral text

No time estimates, correct types and statuses, and team-visible text that never names a bot or vendor upstream.

Principle
  • No time estimates, timeboxes or day counts in tickets, PRDs or outlines.
  • Every ticket gets a real task type (Bug, Spike, Task…) and the list's proper status.
  • Team-visible text is neutral: no bot names, no "Created by…" attribution lines, no upstream project names the product is derived from.
  • Descriptions contain the actual information, with source links at the bottom.

Why it matters

The tracker is the team's shared truth. Estimates written by an assistant are guesses that harden into commitments; bot names and attribution make the work about the tool instead of the outcome; and upstream names leak internals the owner doesn't want public.

Worked examples

Example

Status colours shared across organisations

Both keepers agreed one colour scheme (grey to do, blue in progress, purple review, yellow QA, red blocked, green done) while each workspace keeps its own status names.

Example

Linking PRs

The team links PRs by posting the PR URL as a ticket comment. The keeper only comments when the match is certain (by title or branch).

Templates

Neutral ticket body

## Context
<what and why, plain language>
## Acceptance criteria
- [ ] <observable outcome>
## Links
Spec: <file/PR>   Source: <thread/email>

Pitfalls

  • "Should take 2 days" in a description.
  • "Generated by " footers.
  • Moving a status because work feels done instead of on a PR event.
