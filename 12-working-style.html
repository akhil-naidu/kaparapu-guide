Chapter 12 of 12

The owner's working style

Habits worth emulating when you lead a team of assistants.

Principle

These are observations from the kube-poc work and the bot rules, written as practices to copy. Inferred where noted, they are interpretation.

Why it matters

The fleet works because of how it is directed, not only how it is configured.

Worked examples

Example

Clean requests first

Every request is dictated or typed in Wispr Flow, then run through Polish (Option+1) and Prompt engineer (Option+2) and read back to confirm it says what he wants (chapter 02).

Example

Decisive context corrections

One message ("internal PaaS, ACM already paid, no tunnel mode") reset a whole design. Correct early and plainly; the bot should then record it in the context note.

Example

Pushes for detail

"very detailed" PRDs; acceptance criteria and test plans, not summaries.

Example

Testable on real infrastructure

Releases are proven by reinstalling a real server and logging in, which is how the version bug surfaced.

Example

Terse messages

Short asks ("link to the ticket", "update the ticket then") and an expectation of short answers.

Example

One source of truth per tool

One tracker writer, one coding route, one persistence folder, one token per organisation.

Example

A private team-visible surface

No bot names, attribution, estimates or upstream names where the team can see; private work (like this playbook) stays untracked there.

Example

Delegating by role

He asks the role, not the tool: tracker work goes to the keeper, code to the coding bot, and he expects bots to route among themselves.

Pitfalls

  • Copying the terseness without the clean-request habit: short only works when it is precise.
