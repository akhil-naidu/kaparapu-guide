Chapter 11 of 12

Worked example: kube-poc end to end

Nine steps from one question about a ticket to an approved, phased epic.

Principle

Read each step with the chapter it illustrates in mind.

Why it matters

Rules are easier to remember when you have seen them prevent a mistake.

Worked examples

Example

1. A question about a ticket (ch. 02)

The owner asks the PM bot to explain Spike 01 (production domains and TLS).

Example

2. Research (ch. 04)

The PM bot reads the kube-poc code, the existing product's code, Let's Encrypt limits and Cloudflare's options, and the live Cloudflare zone.

Example

3. Context correction → PRD (ch. 05, 12)

The owner corrects the framing: "this application … is not for distributing to multiple users, we use it internally … as our paas", ACM is already paid for, and "tunnel mode is not required, create a PRD … very detailed". The spike becomes a detailed PRD without tunnel mode.

Example

4. Keeper updates the tracker (ch. 01, 03)

"update the ticket then" → handoff to the keeper, which updates the ticket and returns the link.

Example

5. Coding bot releases (ch. 07)

The coding bot cuts v0.0.2 and v0.0.3 and opens PR #6 to stamp versions into builds.

Example

6. Real-server test finds a bug (ch. 04, 07)

The owner reinstalls a server, sees a version-mismatch warning and asks for a bug ticket. Later he spots /api/v1/info; the bot verifies two issues and the keeper extends the same bug with smoke-test criteria.

Example

7. Architecture decision (ch. 05)

API and user-model questions establish that the platform has users and namespace roles but no teams or user API. Decision: Cloud owns orgs, billing and auth; kube-poc trusts tokens Cloud signs, scoped to an org's namespaces.

Example

8. Phased order (ch. 05)

The PM bot proposes 7 phases. The owner catches two tickets that belong to other work, so they're removed and a kube-poc tag is added to prevent mix-ups. That leaves 19 tickets.

Example

9. Approved as an epic (ch. 10)

The owner makes it a top-level epic with sub-tickets, executed phase by phase, one ticket at a time, with clean statuses and comments.

Pitfalls

  • Reading this as a script: the value is in the corrections at steps 3 and 6.
