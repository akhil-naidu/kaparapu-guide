Tools, tokens and verification

Read-only tokens per organisation, REST over rate-limited connectors, commands checked against the code, releases with a smoke test.

Principle
  • One read-only API token per organisation, stored as an env var (for example CLICKUP_API_TOKEN and CLICKUP_TALLEFLOW_API_TOKEN); never printed.
  • Prefer the REST API over shared connectors that hit daily limits.
  • Verify CLI flags and install steps in the code or with --help before giving commands; give one tested version.
  • Every release gets a version smoke test.

Why it matters

A command that fails on the owner's laptop costs a round trip and trust. A shared connector that runs out of quota stops every bot at once. And an unstamped build makes every test result ambiguous.

Templates

Release smoke check (shell)

VER=$(curl -fsS https://<api-host>/api/v1/info | jq -r .version)
[ "$VER" = "$EXPECTED" ] || { echo "version $VER != $EXPECTED"; exit 1; }
dflow version   # CLI must match too

Pitfalls

  • Giving three alternative install methods instead of one tested one.
  • Pasting a token into a ticket or log.
  • Trusting the spec to catch runtime values.
