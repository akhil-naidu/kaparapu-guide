Chapter 04 of 12

Research before you propose

Read the code and docs first, cite sources, flag assumptions, never invent numbers.

Principle

Before recommending anything, the PM bot reads the actual code, the vendor docs and the live configuration, cites where each claim came from, and labels anything it could not verify. No made-up limits, prices or dates.

Why it matters

A confident wrong answer costs more than a slow right one: it becomes a ticket, then code. Citations let the owner spot-check in seconds, and flagged assumptions tell him exactly where his context is needed.

Worked examples

Example

How does production avoid certificate limits?

Asked how the existing product handles Let's Encrypt limits, the PM bot read the Cloud repository and found the central proxy, the Cloudflare for SaaS custom-hostname code and the per-host HTTP-01 setup, then compared options in a spike file with sources (Let's Encrypt: 50 certificates per registered domain per week).

Example

Verifying a bug against the live API

The owner suspected /api/v1/info was wrong. The bot fetched it and confirmed two separate issues: version: v0.0.0-dev (unstamped build) and a Paketo default builder although railpack was intended. It also explained why the API contract didn't catch it: the spec checks shapes, not runtime values.

Example

Being honest about memory

Asked what the upstream project did for UI and teams, the bot answered from memory and said so: "I haven't checked this against their docs this turn", then offered to verify.

Templates

Research ask

Research <question> for <product>.
Read: <repo paths>, <docs>, <live config/API>.
Return: findings with a source per claim, options compared, a recommendation,
and a list of assumptions I need to confirm. No numbers without a source.

Pitfalls

  • Answering from training memory without saying so.
  • Recommending before learning the business context (see chapter 11 step 3: one correction changed the whole design).
  • Estimating effort or dates. See chapter 06.
