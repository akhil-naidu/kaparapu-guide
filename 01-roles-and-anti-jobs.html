Chapter 01 of 12

One bot, one job

Give every assistant a single job and an explicit list of things it must never do.

Principle

Each bot owns exactly one job and has written anti-jobs. Roles are mirrored per organisation (one keeper, one coding bot, one content bot each); general bots serve the owner across everything.

Why it matters

When one assistant researches, edits the tracker and writes code, nobody can tell which change came from where, and approvals get blurred. Single jobs make every action traceable to one role, keep instructions short, and let you tune or replace one bot without touching the rest.

A single writer per system is the key idea: only the keeper writes to the tracker; only the coding bot touches repositories.

Worked examples

Example

The roster

  • PM / research bot: research, spikes, PRDs, epics, ticket reviews. Anti-jobs: never edits the tracker, never writes code or PRs.
  • Ticket-keeper bot: the only tracker writer; sweeps PRs against tickets, keeps the action list. Anti-jobs: no code, no ticket creation without approval.
  • Coding bot: code, PRs, releases, only through cloud agents in the organisation's Cursor Project; logs every agent it launches. Anti-jobs: no tracker writes, no merges without the owner.
  • Email triage bot: reads and sorts mail, drafts. Anti-job: never sends without approval.
  • Personal advisor bot: digests and priorities across everything. Anti-job: no org writes.
  • Fleet-admin bot: designs bots and pushes approved process fixes to them. Anti-job: no product work.
Example

The org operating model: three roles per org

Every organisation has three top-level roles. Designer and reel bots are separate and optional.

  1. Product manager: thinks like a PM. Writes spikes and PRDs, envisions epics, and reviews the developers' work and decisions. Never edits the tracker directly; asks the keeper to create, comment on or assign tickets.
  2. Work keeper (tracker bridge): the only bot working in the tracker. Turns the PM's vision into epics, stages and tickets, comments and assigns, and reports team decisions and progress back to the PM. It is the bridge between the PM, the coding bot and the rest of the org.
  3. Coding bot (executor): picks up tickets and epics from the keeper (keeper tickets are its priority) and executes in the org's Cursor Project. Senior-developer level control, draft PRs, no merge or deploy without the owner's OK.

Flow:

  1. PM sets the vision (spike / PRD / epic).
  2. Keeper creates the epic and tickets.
  3. Coding bot executes and opens a draft PR.
  4. PM reviews the work and decisions.
  5. Keeper comments and assigns based on the review.

Example

A handoff instead of a shortcut

In the kube-poc work the owner said "update the ticket then". The PM bot had the API token and could have edited the ticket itself. Instead it sent the rewritten PRD to the keeper bot, which updated the ticket and replied with the link. The PM bot then confirmed to the owner only after the keeper reported back.

Example

Naming by role, not by bot

Bots get a fitting character name for the owner's convenience (a navigator for the keeper, a strategist for the PM). That name never leaves the owner's chat: see chapter 06.

Templates

Role card (paste into a bot's instructions)

ROLE: <PM / research bot> for <organisation>.
JOB: research, spikes, PRDs, epics, ticket reviews for <products/repos>.
ANTI-JOBS:
- Never edit the tracker. Hand tracker changes to the keeper bot.
- Never write code or open PRs. Hand code work to the coding bot.
- Never send email or post to team channels; drafts only.
HANDOFFS: carry the owner's exact words and the time (see chapter 03).
READ FIRST: /persistence/INDEX.md and <org>/context.md.

Pitfalls

  • Letting a bot "just quickly" do another bot's job because it has the access. Access is not permission.
  • Two bots writing to the same system: you will get duplicate tickets and conflicting statuses.
  • Mixing organisations in one bot. Mirrored bots share process, never org data.
