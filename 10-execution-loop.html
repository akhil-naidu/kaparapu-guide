The phase-by-phase execution loop

One ticket at a time: spike, approve, track, implement in a cloud agent, PR, test, retro.

Principle
  1. Pick the next ticket in the epic order.
  2. PM bot writes or refreshes the spike / PRD.
  3. Owner approves (his words, quoted).
  4. Keeper updates the ticket and status.
  5. Coding bot launches a Cursor cloud agent in the organisation's Project; draft PR.
  6. Owner tests on real infrastructure.
  7. Status moves only on PR events (opened → review, merged → QA/done).
  8. Retro note: a learnings row and a changelog entry.

Why it matters

One ticket in flight keeps statuses truthful and comments clean, and makes every failure easy to trace to one change.

Worked examples

Example

Where kube-poc enters the loop

Phase 1 starts with the version-mismatch bug (merge PR #6), because until it lands every test runs on a v0.0.0-dev build.

Templates

Loop kick-off

Next ticket: <url> (phase <n>).
1) PM: refresh spike/PRD, list open questions.
2) After my OK: keeper -> in progress; coding bot -> cloud agent, draft PR.
3) I test on <server>. Status moves on PR events only.
4) Retro: one learnings row.

Pitfalls

  • Starting ticket two while ticket one waits for review.
  • Commenting progress on the ticket instead of in chat.
  • Skipping the retro note.
