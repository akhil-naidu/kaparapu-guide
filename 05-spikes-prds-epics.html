Spikes, PRDs and epics

Three document shapes turn questions into decisions and decisions into ordered tickets.

Principle

Spike answers a question. PRD specifies what to build once the answer is known. Epic orders the resulting tickets with acceptance criteria and dependencies. Files live in the persistence folder; tickets link to them.

Why it matters

Mixing the question with the spec produces tickets that are half research, half build, which can't be accepted cleanly. Separate shapes give each ticket a clear "done".

Worked examples

Example

Spike → PRD

The TLS research spike ended with a decision section linking to the rewritten Spike 01 PRD (wildcard Origin CA certificate as the proxy default, no per-app Let's Encrypt, Cloudflare for SaaS custom domains ported from existing code).

Example

A standalone spike

The owner asked for dflow upgrade as "a new, separate one", not a continuation. The spike compared self-update libraries, found that versions weren't stamped into builds, and ended with a ticket breakdown.

Example

The epic

Seven phases, 19 sub-tickets (two non-kube-poc tickets were removed after review, and every kube-poc ticket now carries a kube-poc tag), ordered so every feature hangs off a stable foundation: release pipeline, platform foundations, resource model and tenancy, app runtime, data services, templates, console.

Templates

Spike

# Spike: <question>
1. Question (one sentence)
2. Context and current state (with file paths)
3. Options considered
4. Findings, each with a source
5. Recommendation
6. Risks and open questions
7. Proposed tickets (title + acceptance criteria)

PRD

# PRD: <title>
1 Problem  2 Decision summary  3 Context / current state
4 Users  5 Goals and non-goals  6 Detailed requirements
7 UX flow (CLI and UI contract)  8 Security  9 Observability
10 Success metrics (qualitative)  11 Rollout  12 Test plan
13 Acceptance criteria  14 Open questions  15 Risks  16 References

Epic

# Epic: <outcome>
Execution: phase by phase, one ticket at a time.
Phase 1 – <name>
  - <ticket>: AC: <...>  Depends on: <...>
Phase 2 – ...
Parallel: <which phases may overlap>
Rules: no time estimates; status moves only on PR events.

Pitfalls

  • Success metrics with invented numbers; keep them qualitative unless sourced.
  • PRDs that silently keep an option the owner removed (the rewrite dropped tunnel mode entirely).
  • Epics without dependencies; the order is the value.
