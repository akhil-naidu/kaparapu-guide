Working with AI: an organisation playbook

How one organisation runs product work with a small fleet of AI assistants: chat bots with single jobs, Cursor cloud agents for code, and a human who approves every step that leaves the box. Every rule here comes from real work on a real product.

Start readingJump to the worked example

What this playbook is

A guide to working with AI inside one organisation. It merges the habits of an owner who runs several bots day to day into a single set of practices: who does what, how approval flows, how research turns into tickets, how tickets turn into PRs, and how the process remembers what it learned.

The running example is a real internal-platform project (a Kubernetes-based PaaS, called kube-poc here) taken from a first question about one ticket all the way to an approved, phased epic.

Bot roles

One job each, plus explicit anti-jobs. Arrows show handoffs; only the keeper touches the tracker and only the coding bot touches code.

Human owner

Decides, approves, corrects context. The only source of approval.

PM / research bot

Research, spikes, PRDs, epics, ticket reviews. Never edits the tracker, never writes code.

Ticket-keeper bot

The only bot that writes to the tracker. One per organisation.

Coding bot

Code, PRs and releases, only through the organisation's Cursor Project cloud agents.

Email triage bot

Reads and sorts mail, drafts replies. Never sends without approval.

Personal advisor bot

Digests, priorities, cross-cutting advice. No org writes.

Fleet-admin bot

Designs and tunes the bots and their instructions. No product work.

How to read it

  1. Read chapters 01 to 10 in order. Each builds on the previous one: roles, clean requests, approvals, research, documents, the tracker, tools, communication, memory and finally the execution loop.
  2. Chapter 11 replays the whole kube-poc story step by step, linking back to the rule each step illustrates.
  3. Chapter 12 describes the owner's working style: the habits that make the rest work.
  4. Copy templates straight from the grey boxes. Text marked Inferred is interpretation, not a recorded rule.

Chapters

01

One bot, one job

Give every assistant a single job and an explicit list of things it must never do.

02

Write a clean request before you send it

Dictate or type the ask, run it through a polish and a prompt-engineer pass, read it back, then send.

03

Approvals travel with the work

Only the human approves. Every handoff carries the exact approval words and a timestamp.

04

Research before you propose

Read the code and docs first, cite sources, flag assumptions, never invent numbers.

05

Spikes, PRDs and epics

Three document shapes turn questions into decisions and decisions into ordered tickets.

06

A clean tracker and neutral text

No time estimates, correct types and statuses, and team-visible text that never names a bot or vendor upstream.

07

Tools, tokens and verification

Read-only tokens per organisation, REST over rate-limited connectors, commands checked against the code, releases with a smoke test.

08

Concise messages, at the right time

At most one short "on it", then one result message. Respect working hours.

09

Shared memory and living docs

Persist decisions in one indexed folder; let paired bots share process learnings, never org data.

10

The phase-by-phase execution loop

One ticket at a time: spike, approve, track, implement in a cloud agent, PR, test, retro.

11

Worked example: kube-poc end to end

Nine steps from one question about a ticket to an approved, phased epic.

12

The owner's working style

Habits worth emulating when you lead a team of assistants.
